# Intake Decisions

## D-01: Adapt The Research Structure To Intake

Use `.intake/research/` for source, question, contradiction, decision, and synthesis records instead of creating a separate research system. This preserves the repository's intake trust boundary and avoids duplicate process scaffolding.

## D-02: Separate Observation, Direction, And Derivation

Label current implementation observations with locked source revisions. Label owner-confirmed target behavior as direction. Label normalized contracts and taxonomy choices as derived design.

This prevents an accepted future architecture from being reported as deployed behavior.

## D-03: Keep Private Evidence Referential

Record private repository paths, revisions, and hashes in source locks. Publish transformed criteria and contracts rather than copied private content.

## D-04: Treat Content Diagnosis As Core SEO Work

Use the content repositories to teach the SEO agent how to identify content-related deficiencies and distinguish them from other causes. Use their downstream schemas to formulate a precise implementation brief when intervention is justified.

Do not include drafting instructions or finished-copy production.

## D-05: Design The Smallest Stable Recipe Contract

Require only identity, discovery, input, capability, bounded method, evidence, stopping, completion, and output-contract information needed by the initial client-executed model. Defer persistent run state and a general component language.

## D-06: Keep Runtime Availability Server-Resolved

Public definitions declare requirements. The authenticated server resolves current visibility, retrieval, execution, cost, and reason codes. Agents never infer entitlement from public recipe presence.

## D-07: Use Examples As Contract Tests

Create a small representative set that tests different decision boundaries instead of one fixture per recipe or metadata field. Expand the set only when a distinct failure mode appears.
